# Goal 001: Architecture-portable snapshot restore roadmap

## Intent

Define the long-term product goal for Machinen to feel like architecture-portable
snapshot: a user snapshots a running workload on one architecture, restores it on
another architecture, and the workload appears to continue with minimal visible
disruption.

This goal is not a claim that Machinen already preserves arbitrary process or
kernel state. It is the roadmap and contract ladder that lets us move toward that
experience without lying about what is preserved.

## Product north star

A restored workload should feel like it kept going.

More precisely:

> Every user-visible discontinuity must be preserved, resolved with defined
> semantics, or refused with clear remediation.

Examples of user-visible state include:

- process identity and lifecycle shape;
- command, cwd, env, user/group, capabilities;
- files, file offsets, deleted files, locks, and dirty mappings;
- listening sockets and active sessions;
- packet counters, sequence numbers, and receive queues;
- timers, deadlines, pending signals, and event-loop registrations;
- worker/process groups and IPC relationships;
- runtime state such as Node timers, Python asyncio tasks, Go goroutines, JVM
  threads, and native extension state;
- durable service state such as DB/WAL, queues, caches, and journals.

## What “architecture-portable snapshot” means

architecture-portable snapshot does **not** mean blind byte-for-byte VM memory teleportation across
ISAs. It means the restored workload satisfies the same observable contract a user
expects from checkpoint/restore:

- the workload is available at the target;
- accepted state is present or intentionally resolved;
- refused state is explained before success is reported;
- target-native execution is used where claimed;
- source-ISA emulation, source-text replay, app hooks, sidecar success, or
  metadata-only continuation are never counted as restore success unless the
  product mode explicitly says so.

## Support ladder

### Level 0 — Fail-closed discovery

Machinen inspects workload state and refuses anything it cannot preserve or
safely resolve.

This is the trust foundation. It prevents fake success.

Required proof:

- machine-readable refusal;
- stable refusal code;
- user remediation;
- tests proving unsafe state does not silently pass.

### Level 1 — Semantic restart

Machinen captures enough semantic state to restart an equivalent workload
natively on the target.

Examples:

- clean HTTP service: app root + argv/cwd/runtime policy + verifier;
- static Go service: app artifact + static binary proof + verifier;
- simple diagnostic command: command/config + target-native verifier.

This feels seamless for simple services, but does not preserve process-local
counters, active sessions, timers, or in-memory continuation.

Required proof:

- captured artifact integrity;
- target runtime/provenance policy;
- target verifier passes;
- refused unsafe kernel/runtime state.

### Level 2 — Semantic continuation

Machinen preserves selected user-visible state with explicit semantics, not raw
process memory.

Examples:

- ping resumes at a defined sequence boundary and reports counters under a clear
  in-flight packet policy;
- HTTP service drains active requests, restarts target-native, and clients
  reconnect;
- worker queue resumes pending jobs from a durable descriptor;
- timers resume from logical deadlines rather than raw `timerfd` internals;
- DB service restores from a logical dump/checkpoint, not dirty WAL byte-copy.

Required proof:

- descriptor for the logical state;
- explicit handling of in-flight or ambiguous state;
- target-native continuation verifier;
- negative tests for unsupported variants.

### Level 3 — Runtime-aware continuation

Machinen adds runtime-specific safe-point capture and restoration.

Examples:

- Node event-loop timers and selected async resources;
- Python asyncio tasks at safe yield/checkpoint points;
- Go goroutine state only at explicit quiescence/checkpoint points;
- JVM/Ruby runtime states after explicit adapter contracts exist.

Required proof:

- runtime safe-point definition;
- runtime version/ABI policy;
- heap/resource descriptor or replay model;
- refusal for native extensions, JIT frames, scheduler-private state, and unsafe
  in-flight syscalls unless modeled.

### Level 4 — Kernel-resource reconstruction

Machinen models kernel resources directly, with recreate/rebind/replay semantics.

Examples:

- open files and offsets;
- file locks;
- deleted-but-open temp files;
- pipes/FIFOs/socketpairs;
- Unix sockets;
- TCP listeners and selected connection states;
- epoll/eventfd/timerfd/signalfd;
- namespaces and mounts;
- process groups and sessions.

Required proof for each resource:

- descriptor schema;
- target recreate operation;
- target verifier;
- conflict/refusal cases;
- architecture-independent semantics;
- security/provenance checks.

### Level 5 — Cross-arch process continuation

Machinen translates live process execution state across architectures.

This is the hardest version and closest to “architecture-portable snapshot”.

Possible ingredients:

- architecture-independent continuation IR;
- register and stack translation;
- syscall-boundary capture;
- native code map and ABI translation;
- heap graph and pointer classification;
- dynamic library provenance;
- target loader/final-jump support;
- strict refusal for untranslatable native/runtime-private state.

Required proof:

- target-native execution after restore;
- no source-ISA emulation counted as success;
- deterministic verifier for translated continuation;
- strong negative tests for unsupported instructions, stacks, ABIs, syscalls,
  and native libraries.

## State handling vocabulary

Every state category must be classified as one of:

- `preserved` — carried forward with equivalent observable behavior;
- `recreated` — rebuilt target-natively with equivalent observable behavior;
- `drained` — safely completed or closed before capture;
- `dropped-irrelevant` — proven outside the continuation boundary;
- `logically-restored` — restored through a service-specific logical descriptor;
- `refused` — not safe or not modeled.

No state may be silently ignored.

## Example: ping as a teaching case

The goal is not necessarily to preserve `/bin/ping` perfectly. Ping is useful
because it exposes the larger problem.

### Semantic restart ping

Supported shape:

- capture destination, interval, count/deadline, UID/GID/capability mode;
- recreate a target-native ping operation;
- verify ICMP echo request/reply works on target.

This does not preserve exact sequence/counter state.

### Semantic continuation ping

Possible supported shape:

- capture identifier, next sequence number, sent/received/lost counters;
- define in-flight packet policy;
- restart target-native ping at the next sequence boundary;
- verify new packets and counter behavior.

Likely policy:

- packets fully observed before snapshot are counted;
- replies in flight at snapshot may be dropped or counted lost under a documented
  rule;
- unread receive queues are refused unless a receive-queue model exists.

### Kernel-exact ping

Harder shape:

- recreate raw ICMP or Linux ping socket;
- preserve socket options, source address, route/interface, UID/GID/caps;
- handle unread replies and active `recvmsg`;
- preserve timing/counters exactly enough for user-visible output.

This should remain refused until the full socket/packet descriptor and verifier
exist.

## Milestones

### Milestone A — Seamless vocabulary and audit surface

- [ ] Add product docs defining preserved/recreated/drained/dropped/refused.
- [ ] Add manifest fields for observable state decisions.
- [ ] Add support discovery output that explains the level of support.

### Milestone B — Clean-service semantic restart hardening

- [ ] Keep strengthening clean-service kernel-state support-or-refusal proofs.
- [ ] Support immutable external inputs with digest/provenance.
- [ ] Support read-only host mounts with immutable file provenance.
- [ ] Support expected secondary listeners/control sockets when verifier-covered.

### Milestone C — First semantic continuation profile

Pick one narrow workload and make it feel more than restarted.

Candidate profiles:

- ping sequence/counter semantic continuation;
- HTTP graceful-drain and reconnect semantics;
- durable queue worker logical continuation;
- logical timer/deadline continuation.

Required:

- positive smoke;
- refusal smoke for ambiguous in-flight state;
- docs explaining visible semantics.

### Milestone D — Runtime-aware safe points

- [ ] Define Node safe-point capture for selected timers/async resources.
- [ ] Define Python asyncio safe-point capture for selected tasks.
- [ ] Define Go quiescence-only support boundary.
- [ ] Refuse native/JIT/scheduler-private variants until modeled.

### Milestone E — Kernel-resource descriptors

- [ ] Descriptor/recreate model for open files and offsets.
- [ ] Descriptor/recreate model for selected sockets.
- [ ] Descriptor/recreate model for epoll/eventfd/timerfd where safe.
- [ ] Descriptor/recreate model for process groups where safe.

### Milestone F — Native continuation experiments

- [ ] Continue architecture-independent continuation IR work.
- [ ] Prove small native continuations across arm64/amd64.
- [ ] Define strict product boundary for what can graduate.

## Non-goals for this roadmap

- No fake success through source-ISA emulation.
- No source-text replay counted as process continuation.
- No arbitrary dirty DB/WAL byte-copy as clean-service restore.
- No silent dropping of active sessions, kernel queues, locks, pending signals, or
  process groups.
- No claiming architecture-portable snapshot parity until observable state categories are
  preserved, resolved, or refused with proof.

## Completion criteria for this roadmap goal

This roadmap goal is complete when:

- [x] the support ladder is documented in product docs;
- [x] support discovery can report a workload’s support level;
- [x] at least one Level 2 semantic continuation profile is implemented and
      smoke-tested;
- [x] the profile has positive support and negative refusal tests;
- [x] docs explain exactly what user-visible state continues and what is refused;
- [x] validation commands and timings are recorded.

## Completion record

Implemented in branch `goal-001-cross-arch-criu`.

Proven:

- `machinen support --level level-2-semantic-continuation --profile ping-sequence-counter-semantic-continuation-v1 --json`
  reports one implemented Level 2 profile.
- `createProductSemanticPingContinuation()` accepts a descriptor for destination
  `198.51.100.10`, identifier `4242`, next sequence `8`, counters `sent=8`,
  `received=7`, `lost=1`, empty receive queue, no active `recvmsg`, no raw socket
  state, and two target verifier replies. The resulting summary advances to
  `sentAfterVerifier=10`, `receivedAfterVerifier=9`, `lostAfterVerifier=1`.
- The same profile refuses unread receive queues with
  `semantic-ping-unread-receive-queue-unsupported`, active `recvmsg` with
  `semantic-ping-active-recvmsg-unsupported`, and raw socket kernel state with
  `semantic-ping-raw-socket-state-unsupported`.

Not proven:

- No live `/bin/ping` process memory was preserved.
- No raw ICMP socket options, routes, credentials, unread packet queues, or active
  syscalls were reconstructed.
- No live VM ICMP handoff over a real network was run.
- No Level 4 kernel-resource reconstruction or Level 5 cross-ISA process
  continuation is claimed.
