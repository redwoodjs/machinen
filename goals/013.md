# Goal 013 — Target-VM continuation for Level 4 ping portable restore

## Status

Completed in this change.

## Objective

Make the Level 4 ping portable restore visibly continue the workload on the target machine. Restore must boot a target VM, start target-native `/usr/bin/ping`, and expose live target output.

## Product behavior

`machinen restore ./ping.portable --target-arch <arch>` now uses the normal attached restore mechanics: it boots the target VM and runs target-native `/usr/bin/ping` in the foreground so output streams in the terminal.

`machinen restore ./ping.portable --target-arch <arch> --json` runs the same continuation in detached mode and returns machine-readable restored VM metadata. The JSON mode now:

1. validates the `ping-level4-socket-reconstruction-v1` bundle descriptor;
2. refuses if the requested target architecture does not match the local Machinen guest architecture;
3. boots a target VM;
4. writes the descriptor to `/tmp/machinen-restored-ping-descriptor.json` in the target guest;
5. starts target-native `/usr/bin/ping` using the descriptor destination and interval;
6. writes live output to `/tmp/machinen-restored-ping.log`;
7. verifies a ping process exists and the log contains new `64 bytes from ...` replies;
8. returns JSON with the restored VM name/pid and `migrationCompleted=true`.

## Continuation semantics

The descriptor carries:

- destination: `127.0.0.1`;
- socket kind: `ping-dgram-icmp` or `raw-icmp`;
- echo identifier;
- next sequence;
- interval;
- output log path;
- expected target architecture.

The target uses standard `/usr/bin/ping`. Standard ping does not portably force exact text-output sequence on every target, so Level 4 product semantics are honest:

- the socket/workload intent is reconstructed target-natively;
- destination and interval are preserved;
- echo id and next sequence are preserved in the descriptor and target verifier policy;
- target text output may renumber from the target ping process's own first visible line;
- success requires new target-side replies in `/tmp/machinen-restored-ping.log`.

A stricter future helper can force exact ICMP id/sequence directly by opening the socket itself.

## User flow

Source Mac/arm64:

```sh
pnpm build
WORK=$(mktemp -d)
NAME=ping-e2e
node packages/cli/dist/cli.js boot --detach --name "$NAME" -- sleep 1000
node packages/cli/dist/cli.js exec "$NAME" -- \
  'ping -i 10 127.0.0.1 >/tmp/machinen-ping.log 2>&1 & echo $! >/tmp/machinen-ping.pid'
MACHINEN_SNAPSHOT_ENGINE=portable \
  node packages/cli/dist/cli.js snapshot "$NAME" "$WORK/ping.portable" --json
rsync -a "$WORK/ping.portable/" root@192.168.0.8:/root/machinen-ping-test/ping.portable/
```

Target Proxmox/amd64:

```sh
cd /root/machinen
pnpm build
node packages/cli/dist/cli.js restore /root/machinen-ping-test/ping.portable \
  --target-arch amd64 --json
node packages/cli/dist/cli.js exec <restored-name> -- \
  'cat /tmp/machinen-restored-ping.log'
```

Expected output includes new target-side lines like:

```txt
64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=...
```

## Refusals preserved

Unsafe source states still refuse before a target VM is started:

- zero or multiple ping processes;
- non-loopback destination;
- non-empty queues;
- active receive wait;
- unmatched socket inode;
- architecture mismatch on target restore;
- target verifier/output mismatch.

## Validation

- target VM continuation proof using a synthetic cross-arch descriptor on the local target architecture;
- source Mac/arm64 bundle copied to Proxmox/amd64 and restored with target-side `/usr/bin/ping` output in `/tmp/machinen-restored-ping.log`;
- `pnpm run smoke-portable-ping-machine` for real source ping auto-inspection.
